# OKR 填写与自查助手（产品研发版）

你决定要做什么，AI 帮你把想法写成清楚、可检查的 OKR。

这个项目面向产品研发岗位，帮助你填写和检查自己的 O（目标）与 KR（关键结果）。连接飞书后，项目还计划支持读取 Leader 的 OKR、填写和修改自己的 OKR，以及按你的指令写评论、发通知。

**当前为候选版本（v8，尚未验收）。** 下文先说明项目要解决的问题，再说明目前做到哪一步。飞书侧的评论、通知和修改已有 O/KR 正文，以及新增 O/KR、备注和进展，都已经接入封装与流程，但**只做到预演级别**——真实写入、真实评论和真实发送都还没有验证过。v8 相对 v7 的改动只涉及**填写与审查的互动方式和质量维度**，`tools/okr_feishu.py` 与飞书操作协议**未改动**。

## 它解决什么问题

### 把自己的思考写成合格的 O 和 KR

你需要先想清楚自己的目标、责任范围和希望取得的结果。助手负责帮你梳理表达、检查遗漏和纠正写法，不替你决定这个周期应该做什么。

**你不用先填一张长问卷。** 你已经说清多少，它就先整理多少；每轮只问**当前最影响继续的那一个**问题，其余标「待确认」。只有岗位、还没想出方向时，它先问你这个周期最想推动什么变化，**不会凭空生成一整套工作重点**。

**拆解方式放在具体目标里谈**，不是开场必答题。它可以按你已确认的目标建议一种拆法并举个例子，你选或确认后才落成正式 KR；**你拒绝推荐时，它按你的方式走，不换推另一个**。

填写 KR 时涉及的三种拆解方式：

| 拆解方式 | 回答的问题 |
| --- | --- |
| 策略 | 通过哪些关键路径实现目标？ |
| 维度 | 哪几个方面共同证明目标实现？ |
| 里程碑（任务拆解） | 哪些关键阶段成果决定目标成败？ |

选定一种主拆解方式后，助手根据你的想法整理 O 和 KR，并检查它们是否表达清楚、能否判断结果、能否共同支撑目标。基线、目标值和数据来源需要有依据，不知道的内容标为待确认。

### 填写和审查用同一套质量方法

围绕每个 O 及它下方全部 KR，看五个维度：**业务价值、责任与范围、KR 对 O 的支撑、结果与验收、表达与一致性**。

这五项是**质量建议，不新增硬性判定、得分、排名、达标比例或字数线**；公司现行 🔴／🟠／🟡／⭕ 判据保持不变。**业务价值不等于财务指标**——客户体验、可靠性、研发效率、风险降低、有用的探索结论都算价值，**阶段成果和合理的定性验收也能体现价值**。

### 在飞书里完成读取、填写和沟通

连接飞书后，项目希望让你在同一段对话里完成这些操作：读取自己和 Leader 的 OKR，填写自己的 O 和 KR，向明确指定的 OKR 写评论，并向明确指定的人发送通知。

读取 Leader 的 OKR 是为了了解承接方向。你仍需要判断自己负责什么、准备取得什么结果。写入、修改、评论和通知的内容都先给你核对，确认后再执行。

### 检查自己的 OKR，并完成修改

你可以提供已有的 OKR，也可以让助手从飞书读取。**已有稿就是完整输入，不用先走一遍填写问答。**

它逐个 O **保留你的原文和它下面全部 KR 的原文**，再给问题点。每条问题写清三段：**具体位置和原文依据 → 对价值／支撑／验收有什么影响 → 可怎么改**。

- **硬问题、软建议、资料缺口分清**：🔴 进问题点；🟠／🟡 只提醒、不判不合格；资料不足的单列「待确认」，**既不判通过也不判不合格**
- 可以先突出最影响质量的少数点，但**完整问题与缺口必须保留**，不能删掉或登记成通过
- 符合标准的如实认可，并说明已具备的价值或支撑，**不为了显得严格而挑错**

你可以自己修改，也可以核对修改前后的内容，确认后让助手在飞书更新原条目。

## 使用边界

- 工作重点、责任范围和预期结果由你决定；AI 帮助填写和检查。
- 承诺型、进取型、挑战型的分类由你本人确定，助手不代选。
- 自查面向你自己的 OKR，不评分、不排名，不处理绩效和奖金。
- 只修改你自己的 O/KR 正文及允许的备注。对明确指定的他人 OKR，可以按你的指令评论，不修改对方的 O/KR 正文。
- 通知只发给你明确指定的人，不自动扩大收件人范围。
- 不修改分数、权重、排序、对齐关系或截止日期，不删除数据。

仓库中的三类分类和对应写法来自现有公司管理口径，不是所有公司的通用标准。O/KR 数量用于提醒和检查，不为了凑数量增加工作。进取型每条 KR 的门槛目标需要能判断；挑战型的验证方式与结果证据归到备注。

## 如何开始

只填写和检查文本时，可以安装 [填写技能](skills/product-rd-okr-writer/SKILL.md)，也可以先阅读 [OKR 填写手册](手册-OKR填写要点.md)。安装方式见 [安装技能](docs/01-安装技能.md)。跨 AI 工具的兼容性还未逐家实测。

需要操作飞书时，阅读 [连接飞书](docs/02-连接飞书.md)、[权限清单](docs/03-权限清单.md)和 [命令速查](docs/04-命令速查.md)。飞书功能需要能执行本地命令的 AI 工具，以及本机的 Node.js、Python 3 和 `lark-cli` 环境。

**关于 CLI 版本（如实登记）**：本文命令的参数形状按 **lark-cli 1.0.96** 的 `--help` 核对过。实测发现本机同时存在**多个 `lark-cli`**——npm 全局安装路径下是 1.0.96，而 `PATH` 上的 `lark-cli.CMD` 是 1.0.97。因此：

- 脚本的查找顺序是**：`OKR_LARK_CLI` 环境变量 → `PATH` → `LARK_CLI_CANDIDATES` 固定候选路径**。**`PATH` 优先于固定路径**，所以在本机默认实际命中的是 `PATH` 上那个 1.0.97，而不是当初核对参数时用的 1.0.96。
- 想知道**这台机器上实际会用哪一个**，直接跑（纯本地只读探测，不联网、不碰飞书数据）：

  ```bash
  python tools/okr_feishu.py check-cli
  ```

  它会打印解析到的路径、怎么解析到的、该路径上的真实版本，以及是否与 `SUPPORTED_CLI_VERSION` 一致。
- 要把路径钉死（例如确认要用 npm 那个 1.0.96），设环境变量 `OKR_LARK_CLI` 指向可执行文件。**指向不存在的路径时脚本直接报错、不静默回退**，避免以为钉死了其实没钉死。
- `SUPPORTED_CLI_VERSION = "1.0.96"` 是**声明常量**（记录"当初核对参数时用的版本"），**不是运行时保证**。`check_cli_version()` 与 `check-cli` 子命令只作提醒，**不会因为版本不符就自动停下**。
- 换版本时请以 `lark-cli --version` 与各子命令 `--help` 的实际输出为准。

**目前只验证到预演层，完整连接与真实写入还没有端到端验证过。**

飞书连接由使用者配置自己的应用和登录态。凭据保存在使用者本机安全配置中，不写入仓库或聊天；本地会留下的草案与输出文件见 [安全与凭据](docs/05-安全与凭据.md)。
