# 渐进填写怎么聊

写新 OKR 时读这份。目标是**不用先填一张长问卷**：人已经说清多少，就先给出多少，缺什么就只问当前最影响继续的那一项。

> 这份只管**互动怎么推进**。O/KR 好不好看 [好O好KR标准](quality-standards.md)，成稿格式看 [输出模板](output-templates.md)，硬性口径在 [SKILL.md](../SKILL.md)。

## 一、先用已有内容判断从哪进

进来先看你**已经给了什么**，直接决定这一轮怎么开始。不要给已有内容重新套一遍新手问卷。

| 你已经有的 | 这一轮怎么做 |
| --- | --- |
| 已有的 O/KR 全文 | 直接进入**审查**，不要求先重聊一遍填写流程 |
| 明确的工作重点 + 对结果的想法 | 直接给**局部草稿**，缺的标待确认 |
| 只有岗位，或只有一个泛泛方向 | 先问**本周期最想推动的具体变化**，一次一个 |
| 一次给全了资料 | 直接形成或审查，不强制一问一答 |

## 二、每轮只问一个核心决策点

- **一轮只问当前最影响继续填写的那一项**，用日常语言问。
- 不能写成一条问题、里面却要求同时交范围、指标、协作和拆解。
- **不按「缺几项」批量发题**。缺得多不等于要一次问完——缺得多说明该先问最关键的那一项。
- 用户已经说过的**不再问**。用户补充或纠正后，只更新相应部分，**不重新索要已知资料**。

反例（❌ 一次发五条）：

```text
为了把 OKR 写得贴合你的实际，请补充这几项（已经说过的我不再问）：
1. 你具体负责什么？……
2. 现在最需要解决的问题是什么？……
3. 做成了希望带来什么变化？……
4. 需要哪些人或团队配合？……
5. 每个 O 的 KR 你想怎么拆：策略 / 维度 / 里程碑？……
```

正例（✅ 一次一个）：

```text
我负责的范围我先按你说的记下了。这个季度，你最希望它发生什么变化？
```

## 三、围绕一个 O 边聊边整理

- 用户已经说清**要做什么**和**自己的责任**时，就可以给**暂定 O、结构或已知 KR 草稿**。
- **不等全部字段齐全才展示。** 等齐了再给，等于把人又推回填表。
- 草稿里：已确认的内容**原样保留**；未知的事实**明确标待确认**；**不替用户编数字、编收益、编影响人数**。
- 用户**只给岗位时不生成整套工作重点**。方向没有就先澄清方向——这是工作重点，只能由本人决定。
- 用户**给了多个 O**：先处理最需要推进的那一个，其余**保留**。不为减少阅读负担删掉真实重点。完整审查时仍逐 O 保留全文。

草稿长这样（阶段稿，未定稿）：

```text
阶段草稿（未定稿）

O1（分类：待本人确认）：消除后端服务在高峰期的响应瓶颈
- KR1：核心接口 P95 响应时间改善至【目标值待确认】
- KR2：【待补充：这轮改善覆盖哪些服务，还没定】

已明确：你负责后端服务（范围已记录）
待确认：
- 目标值与基线：你还没给，我不替你拍数
- 分类：只有你和 Leader 能定

下一步：确认 KR2 覆盖范围，或先给 O1 定分类
```

## 四、拆解方式放到具体目标里讲

**不要把「选策略 / 维度 / 里程碑」当每次开场必答题。**

正确顺序：**先有具体目标，再在这个目标里讨论怎么拆**。

1. 用户说清目标后，助手可以**按已确认的主线建议一种拆法**，并**用这个目标举一个简短例子**说明它长什么样。
2. 用户**选或确认后**，才形成正式 KR。
3. 未确认之前只展示「建议」或「草稿」，**标「拆法待确认」**，不能默默替用户决定。
4. 用户**拒绝推荐**时：按用户自己已确认的方式继续，**不回到被拒绝的那个推荐**，也不改推成别的建议。

```text
助手：这个 O「消除后端高峰期响应瓶颈」你已经在推了。
按这个目标看，按「响应时间 / 成功率 / 稳定性」三个维度拆，
每个维度都能各自判断做到没做到，比较容易落到可验收。
这是 AI 建议，你确认或换一个都由你定。

- 维度拆：三个维度各成一条 KR
- 里程碑拆：先做压测定位、再改造热点接口、最后灰度验证
```

> ⚠️ **和「分类只能你定」是两回事**：拆法是**写法选择**，可以商量、可以推荐；**分类是实质判断，不代选、不建议**。

## 五、逐条补结果与验收

- **先问关键成果是什么**，再在需要时补目标值、成功状态或证据。
- **可以用用户已经给出的指标**；**不自行拍数字**。用户答不出数值就保留未知。
- **里程碑允许定性成功状态**，不强求量化——判据是「能不能回答做到什么程度算完成」，**不是「有没有数字」**。
- **只在协作确实影响目标时才追问协作**，不机械重复问五类资料。

## 六、整理时再处理必要确认

- **分类仍由本人选择**，助手不代选、不建议。草稿里可以标「分类待本人确认」，**定稿前补齐**即可。
- **避免每轮重复分类提醒**——定稿前提醒一次就够，不必每轮都问。
- **日期与周期沿用用户已提供的内容**，**不为聊天流程增加强制日期问题**。

## 七、给当前状态和下一步

每轮给一个简短进度说明，让用户知道现在在哪：

```text
已明确：你负责后端服务，要解决高峰期响应慢
待确认：KR2 的覆盖范围、目标值、O1 分类
下一步：确认覆盖范围后我出完整草稿
```

- **用户补充或纠正后，只更新相应部分**，不重新索要已知资料。
- **不把聊天进度汇总写成每轮必须填的表格**。它是给你看的状态，不是交付物。

## 快捷分支

| 用户说 | 你怎么做 |
| --- | --- |
| 一次给全资料 | **直接形成或审查**，不强制一问一答，不规定总共必须聊几轮 |
| 「你先出一版」 | 有主线和责任依据 → 出草稿，未知标待确认；**没有主线 → 先问一个方向问题**，不替用户编工作 |
| 「不知道怎么拆」 | 在其**已确认目标内**给少量写法建议，注明「AI 建议」；取得选择/确认后再落成正式 KR；**不新增用户没提过的重点工作** |
| 「不推荐，就按我说的」 | 按用户已确认方式处理，**不回到被拒绝的推荐**，不另推一个 |
| 暂时答不出数值 | 保留未知，或使用**已确认的定性验收方式**；不因没数字就否定里程碑成果，**也不把草稿标成可直接定稿** |
| 给了多个 O | 先处理最需要推进的一项，**其余保留**；完整审查仍逐 O 保留全文 |

## 首轮示例（只有岗位时）

**互动例子，不是所有场景的固定开场。** 用户换了岗位、换了周期、给了别的内容，开场就换。

```text
用户：我负责后端开发，想写这季度的 OKR。
助手：这个季度，你最希望改善后端服务的哪一个具体问题？
```

对照——不要这样开：

```text
❌ 助手：请补充你的岗位职责范围、当前痛点、期望变化、
   协作方、以及 KR 拆解方式（策略/维度/里程碑），我一次性给你成稿。
```
