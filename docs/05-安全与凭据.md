# 安全与凭据

## 三条红线

1. **不提交凭据。** `app_secret`、token、`.lark-cli/config.json` 里的任何东西，都不能进 Git 仓库。
2. **不传 secret 明文。** 用 `--app-secret-stdin`，别用 `--app-secret xxx`，后者会留在命令行历史里。
3. **不给别人代管凭据。** 每人用自己的账号授权。借别人的 token 用等于把对方的权限借出去。

## 本仓库不需要任何凭据就能用

这是刻意的设计：**技能本体（写 OKR 的部分）零依赖、零凭据**。想读飞书 OKR 才需要自己配一份，配的东西只存在你自己的机器上。

所以：

- 克隆这个仓库不需要任何密钥
- 别人拿到这个仓库也读不到你的任何东西
- 你自己 fork 之后配的 app_id、secret 也不会被我这边看到

## 存在哪、怎么存的

| 东西 | 存哪 | 能不能进仓库 |
| --- | --- | --- |
| App Secret | **系统钥匙串**（macOS 用 `lark-cli config keychain-downgrade` 可降级为本地文件） | ❌ 绝对不能 |
| 用户 OAuth token | lark-cli 自己的本地存储 | ❌ 绝对不能 |
| `~/.lark-cli/config.json` | 明文存 app_id 和用户 open_id；secret 只是一条「去钥匙串取」的引用 | ❌ 不建议，含个人信息 |
| 你的 OKR 内容 | 主要存在飞书系统里；**本地会留下草案与输出文件**，见下一节 | ❌ |

`.gitignore` 已经把这些常见路径排除了，但**提交前还是自己看一眼 diff**。

## 本地会留下什么

「OKR 只在飞书、不落本地」这句话**不准确**，如实说明：

| 文件 | 什么时候产生 | 建议 |
| --- | --- | --- |
| `okr.json` 等草案文件 | 批量写入前，你或助手把成稿存成本地 JSON 交给脚本 | 放在**仓库目录之外**；仓库的 `.gitignore` 也忽略了 `okr.json` / `okr_draft.json` |
| `okr_feishu_output.json` | 终端编码不支持中文时，脚本把命令结果落盘避免乱码 | 已被 `.gitignore` 忽略；看完就删 |
| 命令输出与错误信息 | 每次调用都会打印到终端 | 贴给别人看之前，先检查有没有姓名、open_id、OKR 正文 |

**这些文件都不进 Git，也不要随手贴到群里或 Issue 里。**

## 网络与代理

`tools/okr_feishu.py` **默认保留**你系统的 `http_proxy` / `https_proxy` 设置——企业网络需要代理时不用额外配置。

只有在代理反而导致连接失败时，才显式加 `--no-proxy` 绕过：

```bash
python tools/okr_feishu.py whoami --no-proxy
```

`lark-cli` 本身直接读系统环境变量，遵循它自己的行为即可。

## 工具保护什么、不保护什么

这块容易说大，如实写清楚：

| | 是否由工具强制 |
| --- | --- |
| 默认不写、要显式加 `--execute` 才写 | ✅ 是。预演会打印操作、目标、完整内容和内容指纹 |
| 写入固定用本人身份（`--as user`） | ✅ 是。封装脚本里写死了 |
| 改正文/备注时检测远端是否已变化 | ✅ **默认是**。执行前重读远端比对指纹，对不上就中止；缺指纹直接拒绝执行。**但存在显式关闭例外：`--no-current-check` 会整体跳过这项复核**——加了它就等于放弃远端变更保护，脚本会打印一行提示说明本次未检测 |
| 分类未填/分类不是正整数时拒绝提交 | ✅ 是。本地就拦下，不发请求 |
| 评论定位参数不合法时拒绝提交 | ✅ 是。O/KR 必须**恰好一种**定位（选区/全文/回复）；周期与进展给了选区会被拒；`key-result`/`key_result` 两种拼写都归一到同一底层值 |
| 「你本人确实批准过这次写入」 | ❌ **不是**。`--execute` 只表示执行，工具没有独立的真人门禁，也不能用任何参数证明你批准过 |
| 「这条 O/KR 确实属于你本人」 | ❌ **不是**。**用 `--as user` 只代表以你的身份发请求，不代表这条资源一定归你所有**；工具会把读取到的原始信息打印出来供核对，但归属判断由助手和你确认，脚本不做强制判定，也不会因为 owner 不是你就自动拦下 |
| 「助手一定只在授权范围内读写」 | ❌ **不是**。范围规则靠助手的技能文件约束，工具本身不设白名单 |
| 「CLI 版本符合预期」 | ❌ **不是**。`SUPPORTED_CLI_VERSION` 只是声明常量（记录当初核对参数时用的版本），`check_cli_version()` 与 `check-cli` 子命令仅作提醒，版本不符也**不会自动停止**。本机实测存在多个 `lark-cli`（npm 全局 1.0.96、PATH 上 1.0.97） |

所以：**确认和边界靠流程，机械保护只有上面那几条**。助手不会向你宣称「工具已经强制校验过是你本人同意的」，也不会说「用了你的身份就一定是你的数据」。

⚠️ 例外开关要分清是哪一个：

| 开关 | 作用范围 | 现状 |
| --- | --- | --- |
| `--no-current-check` | 改正文 / 改备注时关闭写前复核 | **存在**，加了会打印提示说明本次未检测远端变更 |
| `--identity` | 读命令（`cycles` / `okrs` / `categories`）的调用身份 | **存在**，默认 `user` |
| `--as-identity` | 仅 `notify` 的发送身份 | **存在**，默认 `user` |
| 写入 / 评论的身份 | `create` / `add-kr` / `update-content` / `patch-notes` / `progress` / `comment-create` | **没有开关**——脚本里写死 `--as user`，使用者改不了 |

所以「可以切换身份」这句话只适用于**读命令和通知**，不适用于写入和评论。

## lark-cli 有多个版本时怎么确认用的是哪个

本机实测同时存在两个 `lark-cli`（npm 全局安装路径下 1.0.96、`PATH` 上的 `lark-cli.CMD` 1.0.97）。脚本查找顺序是：

```text
OKR_LARK_CLI 环境变量（显式指定，优先级最高）
  ↓ 没设
PATH 上的 lark-cli          ← 优先于下面的固定路径
  ↓ 没有
LARK_CLI_CANDIDATES 里的确定路径（npm 全局安装目录等）
```

也就是说，**默认实际命中的是 `PATH` 上那一个**。想确认本机到底会用哪条、什么版本，跑：

```bash
python tools/okr_feishu.py check-cli
```

纯本地只读探测，不联网、不读凭据、不碰飞书数据，会打印解析到的路径、命中方式、该路径上的真实版本，以及是否与 `SUPPORTED_CLI_VERSION` 一致。

要把路径钉死（例如确认要用 npm 那个 1.0.96）：

```bash
# Windows PowerShell
$env:OKR_LARK_CLI = "C:\Users\<你>\AppData\Roaming\npm\node_modules\@larksuite\cli\bin\lark-cli.exe"
```

**指向不存在的路径时脚本直接报错、不静默回退**——避免你以为钉死了、其实又用了 PATH 上那个。

## 加了 `.gitignore` 也不代表安全

`.gitignore` 只对**还没提交**的文件有效。如果凭据已经被提交过：

- 改历史很麻烦（要 rewrite history，会影响所有协作者）
- 更糟的是：**别人已经拉下来了**，改历史不等于撤回

所以原则是：**先配好凭据，再确认 `.gitignore` 生效，最后再提交**。

```bash
git status --porcelain
```

提交前跑一遍，确认没有意外。

## 涉及个人信息的部分

飞书 API 返回的内容里有**姓名、open_id、union_id、邮箱、手机号**。这些：

- 不要贴进 GitHub Issue / PR
- 不要贴进外部聊天工具
- 分享截图前把 ID 涂掉

## 权限的最小化原则

给应用开权限时，**只开你要用的**：

- 只读场景：5 条读权限就够，`writeonly` / `delete` 全都别开
- 三条 `delete` 权限（本项目用不到）**不要开**

权限开多了，一是风险大，二是企业审批容易被卡。

## 一旦出事

| 情况 | 做什么 |
| --- | --- |
| secret 泄露了 | 立刻去飞书开放后台**重置 App Secret**，然后重新 `config init` |
| token 泄露了 | `lark-cli auth logout`，然后重新 `auth login` |
| 误写了飞书数据 | 先用 `lark-cli okr +progress-list` 确认写了什么，再在系统里手动处理 |
| 提交了带 secret 的文件 | 立刻重置 secret（**先做这个**，再去纠结 git 历史） |

**顺序很重要：先重置凭据，再清理痕迹。** 凭据一旦泄露，删文件是不够的。
