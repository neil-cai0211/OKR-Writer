# OKR 写法规范

写 KR 之前读这份。示例只用来体会表达方式，里面的数字不能套用到你的场景。

> **先记住四条公司口径**（细则在 SKILL.md，这里是提醒）：
> ① 每人每周期**通常 3-5 个 O**（建议级，不因数量单独判不合格；只承接一件事时 1 个 O 也可以）；每个 O **通常 2-4 个 KR**——**上限（多于 4 条）只是 🟡 提醒，但下限是硬性的：某个 O 只有 1 条 KR 就判 🔴**。不为凑数编造 KR；确实只有一个成果时，先给「能不能重新审视拆解」的建议，**交本人决定**；
> ② **每个 O 必须选分类**（承诺型/进取型/挑战型），分类只能本人定，AI 不代选；
> ③ 三类 KR 目标写法不同：承诺型给一个必达目标；**进取型每条 KR 都要有门槛目标**（门槛是「最低可接受结果」，不规定必须比目标值小）；挑战型要写清**希望取得的结果**，**验证方式与结果证据写进备注即可（不要求写在 KR 正文）**；
> ④ 基线、公式、口径、数据来源、验收人、验收证据、协作依赖写进**备注**，不塞进 KR 正文。

## 一、O 是什么

O 回答：「本周期最重要的目标是什么，要朝哪个方向行动？」

O 是定性的一句话，讲方向和价值；用结果证明它成没成，是 KR 的活。

## 二、好 O 的六个特征

### 1. 定性为主，不带数字

数字容易让注意力过早锁在指标压力上，也会限制后面的 KR 拆解。数值一律放 KR。

### 2. 动词开头，指向明确

清楚指向要改善、建立、突破或实现的对象。避免「协助、参与、帮助、支持、配合」这类弱责任词。

### 3. 责任范围可控

O 应主要落在你自己能影响的范围内。建议可控度 70% 以上，但这是参考不是硬门槛，别为了凑比例改目标。

### 4. 本周期能完成

能在当前周期形成明确成果或实质进展，不是长期愿景。

### 5. 有挑战感

不只是常规增量任务。理想状态能带来一点「不舒服的兴奋感」——但前提是真实可行，别为了好听吹牛。

### 6. 极简

像一个标题或口号，聚焦一个主题。知识库原文建议 **20 字以内**，这是理想值；公司检查口径是 **O ≤40 字（🟡 提醒）**，超 40 字会被问，但不因此判不合格。专有名词确实长可以适当突破，但不要丢关键信息。

## 三、O 的四种写法

1. `动词 + 名词`：优化支付性能
2. `动词 + 形容词 + 名词`：建立高效的发布流程
3. `副词 + 动词 + 名词`：显著提升交付质量
4. `What + Why`：优化支付性能，支撑大促高峰

优先选最简洁的。What + Why 不是把两个不相干的目标拼起来，Why 必须是 What 直接带来的价值。

## 四、KR 怎么拆：先选主逻辑

一个 O **只用一种**主拆解逻辑，不混用。选定之后再说你的想法；助手负责润色、补口径、纠偏，不替你换主线。你明确说「没思路」，它才在同一方式内给建议，标为「AI 建议」，你确认后才落到正式 KR。

### 1. 按策略拆解

核心问题：**通过哪几条关键路径实现 O？**

适合：增长、改善、转型、跨团队目标。

选 2-4 条最关键的路径，每条转成结果。推荐写法是 `策略方向 + 结果证据`——策略名称本身不是 KR。

例：O「提升重点岗位招聘到岗确定性」，策略法可沿「提高 Offer 接受质量 / 强化到岗前风险管理 / 降低爽约」三条路径设 KR。

策略拆解里可以包含一条最终滞后结果（比如最终的到岗率），但它必须和前面的驱动型 KR 形成因果主线。

### 2. 按维度拆解

核心问题：**哪几个并列方面共同证明 O 成功？**

适合：综合性目标、需要平衡多个面的目标。

例：质量 / 效率 / 交付 / 客户；或者范围 / 合规 / 系统 / 应用。

每个 KR 代表一个核心维度，不要为了面面俱到塞无关维度。

### 3. 按里程碑（任务拆解）

核心问题：**哪些关键阶段成果决定目标成败？**

适合：项目制工作、技术攻关、系统建设、新制度落地，以及本周期还看不出最终业务效果的事。

按关键里程碑推进，每个 KR 写清成果和期限。质量标准和验收人可以放备注。

「完成方案、开发模块、组织测试」是任务；「形成满足核心需求的方案并关闭阻断问题」才是结果化里程碑。

## 五、承接上级 KR：承接结果，不复制文字

「上级 KR 变成我的 O」只表示责任对齐关系，不等于把上级 KR 原文粘到我的 O 栏。

必须完成一次责任转译：

`上级O/KR → 我的责任边界 → 我的独特贡献方向 → 我的O → 我的KR`

你要能回答：

- 我承接的是上级结果的哪一部分？
- 面向什么业务对象或工作环节？
- 我要推动什么变化、创造什么价值？
- 哪些结果由我直接影响，哪些依赖别人？

**风险信号**：如果你的 O 和上级 KR 一字不差，说明方向对但个人转化没做完。把数字或结果状态下移到个人 KR，把 O 改写成你自己可控的方向和价值。

例：上级 KR 是「支付成功率提升至 99.95%」，你的 O 不该原样写成同一句话，可以转译为「消除支付链路的性能瓶颈」，再用 P95 响应时间、重试成功率、异常兜底覆盖率等你能控的驱动结果来证明。只有当整条结果主要归你负责时，才把它作为你自己的最后一条 KR，且前面仍要有你可控的驱动 KR。

别把「得多写点动作」理解成「KR 全写动作」。开发、评审、培训、输出方案这类动作，只有变成有成果、有质量标准、有验收证据的结果或里程碑，才能成为 KR。

## 六、KR 的三种写法

KR 尽量量化，但不强行量化。判断标准首先是「它能不能直接支撑 O、能不能判断目标状态」。能合理量化的尽量量化，不能的就写成有明确成果和期限的定性或里程碑 KR。

### 1. 定量结果型

适合：缺陷率、响应时间、覆盖率、转化率、可用性这类能稳定统计的结果。

推荐结构：`在[截止日期]前，将[指标/状态]改善至[目标值/目标状态]。`

例：`将核心支付链路 P95 响应时间降至 600 毫秒以内。`

目标值和时间边界必须在 KR 正文或 OKR 系统里明确。如果系统已经设了周期和截止日期，正文不用重复写日期。基线、统计对象、公式、数据来源放备注。

### 2. 定性验收型

适合：制度建设、流程建设、机制建设、能力建设、方案设计等不适合硬凑数字的事。

正文写清两件事：**做成什么成果**、**覆盖什么范围**。到达什么标准、谁来验收、拿什么证明，放备注。

不合格：`完善发布流程。`

合格：`建立覆盖需求评审、灰度、回滚、故障复盘的发布流程，明确每个环节的责任人、输入输出和异常处理规则。`

### 3. 里程碑结果型

适合：项目、系统建设、阶段性专项。

推荐结构：`在[截止日期]前，形成/实现[关键成果]。`

不是「完成任务」，而是写阶段成果。比如：`完成支付路由灰度上线，覆盖主流渠道且可按渠道一键回退。`

### 4. 这几种不算 KR

- **进度跟踪**：「持续推进」「及时跟进」「定期同步」属于过程管理
- **动作罗列**：完成开发、组织评审、输出文档
- **伪量化**：文档数量、会议次数、培训场次

只有当进展被转成可验收成果、关键里程碑或结果变化，才能算 KR。

## 七、KR 通用要求

- 每个 O 原则上 2-4 条 KR
- 能量化的尽量量化；数字要对应结果或关键驱动结果，不把活动量当成果
- 增长、降低、提升类 KR 必须写清目标值，基线放备注
- 所有 KR 有明确时间边界，可由 OKR 周期和系统截止日期承载
- 涉及量化指标时，统计对象、公式、数据来源、验收人要在系统备注里可追溯，避免事后改口径
- 平均值、达标率、留存率、性能指标这类会因取数窗口改变结果的，才需要在备注里补取数周期；一次性交付类不用
- 公司已有统一取数规则的，直接继承，不重复说明
- KR 正文里的日期不能和系统周期/截止日期冲突
- 无法合理量化的不要硬编数字凑指标
- 行动计划放 KR 之外，不把工作步骤全塞进去

## 八、好 KR 的九个特征

1. **强支撑**：完成后显著推动 O，全部 KR 完成足以证明 O 有实质进展
2. **结果导向**：衡量发生了什么变化，不只是做了什么
3. **关键聚焦**：只留决定成败的少数结果
4. **清晰具体**：对象、范围、成功状态没歧义
5. **可衡量或可验收**：有数字，或有清晰的定性成果
6. **有时间边界**：在本周期内可验收
7. **责任可控**：你能产生主要影响，协作依赖明确
8. **相互独立且完整**：KR 之间不重复不冲突，合起来覆盖 O 成功的关键证据
9. **有质量护栏**：追速度、数量、增长、效率时，不牺牲质量、安全、合规、成本或体验

## 九、不知道的怎么处理

不得虚构：上级目标、基线、目标值、数据来源、统计周期、验收对象、验收人、验收方式、协作依赖。

这些信息不要求写进 KR 正文，缺失且会影响判断时才由备注或评论承载。

确实没有的，老实标「待确认」。宁可留一个待确认，也不要编一个看起来很专业的数字。
