# 产品研发岗位示例

只用来体会表达方式，**里面的数字不能套用到你的场景**——你的目标值得自己定，不知道就标「待确认」。

## 产品经理

差：`O：完成新一代 POS 需求规划。KR：输出需求文档；组织客户访谈；完成评审。`

问题：全是动作，没说要带来什么判断或变化。

好：`O：验证新一代 POS 在连锁零售场景的核心价值，为版本范围决策建立依据。`

- KR：目标客户关键场景覆盖率提升至【目标值】
- KR：完成代表性客户验证，形成保留、调整或停止的明确决策
- KR：影响版本立项的高优先级需求不确定项全部关闭

## 前端

差：`O：优化商家后台体验。KR：改版 3 个页面；优化加载速度；走查视觉。`

好：`O：消除商家高频操作的卡顿与等待，提升日常经营效率。`

- KR：商家后台核心操作页首屏可交互时间降至【目标值】以内
- KR：订单、商品、库存三大高频任务平均操作步骤减少至【目标值】步以内
- KR：核心流程线上报错率控制在【目标值】以内，且不引入重大回归缺陷

## 后端

差：`O：优化支付性能。KR：完成代码优化；完成压测；输出报告。`

好：`O：突破核心支付链路性能瓶颈，支撑高峰交易稳定运行。`

- KR：P95 响应时间降低至 600 毫秒以内
- KR：目标并发下支付成功率提升至 99.95%
- KR：性能改善后资源占用不突破约定上限，且重大回归缺陷为 0

## 移动端

差：`O：发布 App 新版本。KR：完成开发；提审上架；修复 bug。`

好：`O：把 App 崩溃与卡顿压到用户无感的水平，稳住核心使用体验。`

- KR：崩溃率降至【目标值】以内，且 Top 3 崩溃场景全部关闭
- KR：核心页面卡顿率降至【目标值】以内（口径见备注）
- KR：版本灰度期间回滚次数不超过【目标值】，且无P0级故障

## 硬件研发

差：`O：完成主板开发。KR：完成原理图；完成打板；完成测试。`

好：`O：验证下一代 POS 主板关键方案，为产品立项消除核心技术风险。`

- KR：在约定时间前完成候选方案样机，核心场景功能测试通过率达到验收标准
- KR：性能、功耗、热设计、成本和供应风险均达到立项要求
- KR：关闭所有影响立项的高等级技术风险，形成继续、调整或停止的明确建议

## 测试与质量

差：`O：提高测试质量。KR：新增 500 条用例；执行 3 轮回归；输出测试报告。`

好：`O：提升支付版本的缺陷预防和拦截能力，降低客户上线风险。`

- KR：生产环境支付类逃逸缺陷降低至【目标值】
- KR：核心支付链路自动化有效覆盖率提升至【目标值】
- KR：严重缺陷平均发现阶段前移至约定阶段，且发布窗口不因测试返工延误

## 运维与稳定性

差：`O：保障系统稳定。KR：值班巡检；处理告警；写故障报告。`

好：`O：把核心交易链路的故障影响压到可接受区间，缩短恢复时间。`

- KR：核心交易链路可用性达到【目标值】
- KR：重大故障平均恢复时间缩短至【目标值】以内
- KR：告警有效率提升至【目标值】以上，重复无效告警归零
- KR：全年重大故障复盘完成率 100%（护栏：不靠压制告警达成）

## 架构

差：`O：推进服务化改造。KR：拆 5 个服务；完成技术选型；写设计方案。`

好：`O：解除单体架构对交付速度的制约，让核心业务可以独立发布。`

- KR：核心业务模块达成独立部署，发布不依赖全量回归的比例达到【目标值】
- KR：跨模块变更的平均联调时长降低至【目标值】
- KR：改造期间重大架构级缺陷控制在【目标值】以内，且不停机时间符合约定

## 项目经理

差：`O：推进海外项目。KR：开周会；跟进任务；输出周报。`

好：`O：建立可预测的海外客户版本交付节奏，保障关键上线窗口。`

- KR：关键里程碑按期达成率提升至【目标值】
- KR：跨团队高风险依赖在承诺日期前关闭，逾期关键依赖控制在约定上限
- KR：客户版本一次验收通过率达到【目标值】，并满足严重缺陷护栏

## 研发管理者

差：`O：加强团队管理。KR：组织培训；开展 1 对 1；建设知识库。`

好：`O：降低关键模块的人员依赖，提升团队持续交付韧性。`

- KR：关键模块具备独立维护能力的人员数量提升至【目标值】
- KR：关键模块因单点人员导致的阻塞时长降低至【目标值】
- KR：新人达到独立交付标准的周期缩短至【目标值】，质量不低于团队护栏

## 怎么识别「任务伪装成 KR」

- 「编写 5 份文档」有数字，但仍是动作数量
- 「培训 3 次」有数字，但没证明能力发生变化
- 「完成 100% 开发」只证明范围做完，没说质量
- 「问题关闭率 100%」得先说清范围、等级、重开率和验证方式

把任务升级成 KR 时问自己一句：**做完之后，谁或什么发生了怎样的变化？**

答不上来，说明还停留在动作层面。

## 门槛目标怎么填（进取型专用）

两条要求：

1. **进取型 OKR 里的每条 KR，都要有门槛目标。**
2. **门槛目标要能判断**——数值，或明确的里程碑、判定条件。

位置、括号、措辞都不限——末尾或开头都行，中文括号（）或英文括号 () 都行，叫「门槛目标」「保底值」「最低目标」都行。

门槛目标 = 这条 KR 的**最低可接受结果**，即「最少要做到什么」。

> ⚠️ 门槛**不规定**必须比目标值小还是大。指标越低越好时（响应时间、崩溃率、逃逸缺陷数），门槛的数值会比目标值**更大**；只有越高越好的指标才常见门槛小于目标。

定量 KR：

```text
搭建校招渠道，校招需求达成率 90%（门槛目标：70%）
```

```text
核心支付场景成功率提升至 99.95%（门槛目标：99.80%）
```

> 基线（当前 99.50%）写备注，不写进 KR 正文。

不可量化的 KR 一样要写，写成里程碑或能判断的文字条件：

```text
完成支付路由灰度上线，覆盖主流渠道且可按渠道一键回退
（门槛目标：至少覆盖 Top 3 主流渠道并完成回退演练）
```

```text
建立覆盖需求评审、灰度、回滚、故障复盘的发布流程并试运行
（门槛目标：流程文档通过评审且无阻塞级问题）
```

不合格的一条：

| 反例 | 问题 |
| --- | --- |
| `…（门槛目标：表现良好）` | 分不出做到没做到，不算门槛目标 |

## 同一批 KR 放在三类 OKR 下，写法区别

同一个方向，分类不同，KR 的目标写法就不一样：

**承诺型**（一个必达目标，不拆三档）

```text
O：守住核心交易链路的稳定性底线        [承诺型]
- KR：核心交易链路可用率不低于 99.9%，且 P0 级故障为 0
```

**进取型**（每条 KR 额外写门槛目标）

```text
O：把支付链路的性能与稳定性推上新台阶    [进取型]
- KR：支付链路 P95 响应时间降至 600ms 以内（门槛目标：800ms 以内）
- KR：核心支付场景成功率提升至 99.95%（门槛目标：99.80%）
- KR：灰度期间回滚次数不超过 2 次且无 P0 故障（门槛目标：回滚不超过 4 次且无 P0 故障）
```

**挑战型**（不强制三档数值；结果写在 KR，验证方式与证据放备注）

```text
O：探索零停机发布能力，验证可行性        [挑战型]
- KR：完成零停机发布方案并完成 3 个核心服务的灰度验证

备注：
- 验证方式＝灰度期间业务错误率与监控指标对比报告
- 结果证据＝方案文档 + 灰度数据 + 技术评审结论
```
