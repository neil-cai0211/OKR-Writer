# 输出模板

> 📌 **阶段草稿 ≠ 定稿**：阶段草稿是有效的中间产物，可以缺字段、可以留待确认；**定稿前**分类必须补齐、未知事实必须处理掉。两者不要混。

## 单轮提问（默认形态：一次一个）

**默认不要一次发一整份问卷。** 每轮只问**当前最影响继续的那一项**，用日常语言。

```text
<一句只问当前最关键的那一项的话>
```

- ✅ 「这个季度，你最希望后端服务的哪一个问题得到改善？」
- ✅ 「KR2 你打算覆盖哪几个服务？」
- ❌ 一条问题里同时要求交范围、指标、协作、拆解
- ❌ 「请补充以下 5 项」

**什么时候才多问**：用户明确说「一次给我全部问题」时才发清单。缺得多**不等于**要一次问完——先问最关键的那一项。

**收尾状态**（简短，不是必须填的表）：

```text
已明确：<这轮确定下来的>
待确认：<还缺什么、为什么还不能查>
下一步：<接下来要做什么>
```

> 📌 **「待确认」和「提醒」分开列，不要混写**：待确认 = 资料不足、**查不了**；
> 提醒 = **已查清，确实需要提醒或建议**。把已确认的提醒写成"待确认"是把自己查过的事实说成没查；
> 查不了的写成"没问题"是蒙。详见 [self-check.md](self-check.md) 第八节四种写法对照。

## 阶段草稿（未定稿，边聊边给）

信息不齐时**就给草稿**，不要等齐了再给。已确认的原样保留，未知明确留白。

```text
阶段草稿（未定稿，分类与待确认项补齐后才能定稿）

O1（分类：待本人确认）：<暂定 O>
- KR1：<已确认的内容，原样保留>
- KR2：<已确认的内容；未知部分写【待补充：具体缺什么】>

已明确：
- <你已经说清并被保留的事实>

待确认（资料不足，先不编）：
- <缺什么> —— <为什么不替你填>

下一步：<一个动作>
```

> 📌 **不编数字、不编收益、不编影响人数、不编用户没提过的工作重点。** 用户答不出数值就保留未知；里程碑可以只有定性成功状态。

```text
O：……
KR 拆解方式：策略 / 维度 / 里程碑（AI 建议 / 已确认）
选择原因：……
- KR1：……
- KR2：……
[仅进取型] 每条 KR 都补了门槛目标
[只承接一件事时] 只有 1 个 O，覆盖范围已写在备注

O2（分类：……）
……

O3（分类：……）
……

备注/评论（写进 OKR 系统，不并入 KR 正文）
- 基线 / 计算公式 / 统计口径：
- 数据来源：
- 取数周期（仅当会影响结果时）：
- 验收人与验收证据：
- 协作依赖：

- 业务价值：<改善谁的什么问题，完成后有什么变化>
- 责任与范围：<本人可控部分 / 协作依赖>
- KR 对 O 的支撑：<每条 KR 怎样推动 O；全部完成是否足以证明 O 有实质进展>
- 结果与验收：<成果还是动作；对象/边界/目标或成功状态/证据>
- 表达与一致性：<是否清楚简练、有无歧义、分类是否一致>

- ……

- ……

- 数量与结构：……（是否 3-5 个 O；**有没有哪个 O 只有 1 条 KR（🔴）**；有没有多于 4 条的（🟡）；分类是否齐全）
- 门槛目标：…… / 本轮不适用（无进取型 KR）
- O 的质量：……
- KR 的质量：……
- 护栏：……
```

## 场景 C：检查自己已有的 OKR

你直接给出已有稿（粘贴，或接了飞书由助手读取指定周期的正式内容）时用这个。**先审已有全文，不要求先完成填写问答。**

```text
场景：检查自己已有的 OKR

检查对象：本人 · <周期>（粘贴稿 / 飞书读取）
检查范围：本次只查你给的这份稿，不扩到其他周期或其他人的 OKR

O1：<原文逐字保留>
- KR1：<原文逐字保留>
- KR2：<原文逐字保留>
（该 O 下几条 KR 就列几条，一条不省）

这个 O 的问题点
- <位置：哪一条 KR / O 的哪一段> ｜ 原文依据：<原文摘录>
  ｜ 影响：<对价值／支撑／验收有什么影响>
  ｜ 建议：<可怎么改> ｜ 级别：🔴/🟠/🟡

已具备（合格处如实写明价值或支撑，不为显得严格而挑错）
- ……

O2：<原文逐字保留>
……

总体结论：存在问题 / 暂未发现明显问题

待确认（资料不足、这一项查不了——**单列且完整保留，不默认通过**）
- <哪一项>：<缺什么才能查>

提醒（已确认、确实需要关注；与上面的"待确认"分开）
- ……

修改建议汇总（只给建议，不改原文）
- ……
```

**规则**：

- **每个 O 的原文和它下面全部 KR 的原文都要完整保留**，再给这个 O 的问题点和建议
- 每条问题写清三段：**具体位置和原文依据 → 对价值／支撑／验收的影响 → 可怎么改**
- 符合标准的 O 就写「暂未发现明显问题」，**并说明已具备的价值或支撑**，不为了显得严格而挑错
- **硬问题、软建议、资料缺口分清**：🔴 进问题点；🟠／🟡 写进「提醒」且**不判不合格**；资料不足的写进「待确认」，**既不判通过也不判不合格**
- **资料缺口多于 3 项也要全部保留**——可以先突出最影响质量的少数点作为当前展示重点，但**不能把其余未确认事项删掉或登记成通过**
- 只审核时**只输出建议**，不写回飞书、不写评论、不发通知
- 我只说「帮我改成能用的版本」时，才在诊断之后追加「原文 → 建议稿」，保持原 O/KR 对应，未知事实仍标「待确认」
- 总体结论只能是「存在问题」或「暂未发现明显问题」，不打分、不排名



## 三个完整示例（含分类与门槛目标）

### 示例 1 · 进取型（每条 KR 必须带门槛目标）

```text
O1（分类：进取型）
O：突破核心支付链路性能瓶颈，支撑高峰交易稳定运行
KR 拆解方式：维度
- KR1：核心支付场景成功率提升至 99.95%（门槛目标：99.80%）
- KR2：支付链路 P95 响应时间降至 600ms 以内（门槛目标：800ms 以内）
- KR3：目标并发下资源占用不突破约定上限，且重大回归缺陷为 0
      （门槛目标：无 P0 缺陷，资源占用不超过当前 1.5 倍）

备注（O 层）：
- KR1 基线：当前 99.50%（来源：核心交易链路监控，近 3 个月）
- KR2 基线：当前 1.2s（同上）
- 门槛目标的「更低/更高」方向按指标性质定：成功率类门槛低于目标值，
  响应时间/耗时类门槛高于目标值，不是所有指标都要求门槛小于目标
```

### 示例 2 · 承诺型（一个必达目标，不拆三档）

```text
O2（分类：承诺型）
O：守住核心交易链路的稳定性底线
KR 拆解方式：维度
- KR1：核心交易链路可用率不低于 99.9%，且 P0 级故障为 0
- KR2：重大故障平均恢复时间控制在 30 分钟以内
- KR3：监控告警覆盖率达到 100%，无误报漏报升级为线上事故
```

⚠️ 承诺型是「必须守住」的目标，目标值按能守住的水平来定，不要写够不到的数字。

### 示例 3 · 挑战型（结果写在 KR；验证方式与证据放备注）

```text
O3（分类：挑战型）
O：探索零停机发布能力，验证可行性
KR 拆解方式：任务
- KR1：完成零停机发布方案并完成 3 个核心服务的灰度验证
- KR2：形成继续投入、调整或停止的明确决策建议

备注/评论
- KR1 验证方式＝灰度期业务错误率与监控指标对比报告；
  结果证据＝方案文档 + 灰度数据 + 技术评审结论
- KR2 验证方式＝季度末技术评审会纪要；
  结果证据＝评审通过的结论文档
```

## 只有任务、还不构成 OKR 时

先说清为什么，再给升级方向，不硬凑：

```text
判断：目前还只是一个任务，不建议直接作为 OKR
原因：……（比如只描述了动作，没说明要带来的变化）

建议的升级方向
- 补齐价值：完成后谁或什么会发生怎样的变化？
- 补齐结果：用哪 2-4 个结果证明这件事成了？
- 补齐边界：你能控到哪一步，哪些依赖要先确认？
- 补齐分类：它属于承诺型、进取型还是挑战型？（这个问题只有你和 Leader 能答）

补齐之后可以这样写
O1（分类：待本人确定）
O：……
- KR1：……
```

未知事实仍标「待确认」，不替用户编造业务结果。
